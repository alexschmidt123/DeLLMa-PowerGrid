# Codebase Research Summary — DeLLMa-PowerGrid

> Generated by code inspection. All claims are grounded in the actual source files.

---

## 1. What the current DeLLMa code is trying to do

DeLLMa (**De**cision-making with **L**arge **L**anguage **M**odels **a**gents) is a prompting framework that turns an LLM into a **decision-making agent under uncertainty**.

The core workflow is:

```
Context (domain data)
    + Actions (what the agent can choose)
    + State beliefs (uncertainty about relevant factors)
    + Preference elicitation (rank state-action pairs)
        ──────────────────────────────────────────────
        → LLM prompt(s)
        → OpenAI API call(s)
        → JSON response with decision + explanation
        → evaluate against ground-truth oracle
```

The framework supports three prompting modes:
| Mode | Description |
|------|-------------|
| `zero-shot` | Single prompt, ask LLM to pick directly |
| `self-consistency` | Multiple samples, majority vote |
| `cot` (chain-of-thought) | Multi-turn: first elicit uncertainty, then decide |
| `rank` | Sample state-action pairs, ask LLM to rank them |
| `rank-minibatch` | Same as rank, but split into overlapping minibatches |

---

## 2. Research purpose

The research tests whether LLMs can make **economically/operationally rational decisions under uncertainty** in structured domains, benchmarked against oracle ground truth.

Three domains are implemented:
| Domain | Agent | Oracle |
|--------|-------|--------|
| Agriculture | `FarmAgent` | Maximize yield × price for fruits in California |
| Stock trading | `TradeAgent` | Maximize return over Dec 2023 for 7 stocks |
| **Power grid** | `PowerGridAgent` | **Identify most unstable microgrid regime (highest mean `stab`)** |

---

## 3. How the power-grid adaptation is framed

**Dataset:** `Data_for_UCI_named.csv` — 10,000 simulated scenarios of a 4-node smart grid.

Each row has:
- `tau1..tau4` — participant response time constants
- `p1..p4` — power injection/consumption per node
- `g1..g4` — pricing/control gain coefficients
- `stab` — continuous stability margin (`< 0` = stable, `> 0` = unstable)
- `stabf` — binary label (`stable` / `unstable`)

**Pre-processing:** `data/powergrid/cluster_split.py` uses k-means (`k=7`) on the 12 `tau/p/g` features to create `cluster_00.csv` … `cluster_06.csv`.

**Task framing:** Given a subset of `k` clusters (choice-set size `k ∈ {2..7}`), the agent must **select the single most unstable cluster** (highest mean `stab`) to prioritize for grid protection under a limited budget.

**Prompt information given to LLM:** Per-cluster mean/std of `tau`, `p`, `g` + last 5 sample rows (feature columns only; `stab`/`stabf` muted by default).

**Oracle:** `np.argmax(mean_stab)` over the candidate clusters (updated to unstable-first objective).

**Metrics:**
- **Accuracy** — fraction of choice sets where LLM picks the same cluster as oracle
- **Regret** — `oracle_mean_stab − predicted_mean_stab` (lower is better; 0 = perfect pick)

---

## 4. Inputs, outputs, and decision variables

| Element | Description |
|---------|-------------|
| **Input** | Per-cluster data summaries (tau/p/g stats + sample rows) |
| **Actions** | Allocate full budget to one cluster: `Action i. cluster_XX: 10000 budget units` |
| **State variables** | 5 agnostic (load error, renewables, etc.) + 3 per cluster (overload risk, response margin, stability outlook) |
| **LLM output** | JSON with `decision`, `rank` (rank mode), `explanation` |
| **Evaluation input** | Saved `response_*.json` files in `results/` |
| **Oracle** | Mean `stab` per cluster from CSV |

---

## 5. Pipeline type

This is a **LLM-driven ranking / selection pipeline**, not a classifier or regression model.

The LLM is not trained or fine-tuned. It is used purely for inference-time decision-making via prompt engineering. Evaluation is offline (compare saved responses to oracle).

## 8. Open questions / ambiguities from the codebase

1. **State beliefs are flat / uninformative for powergrid.**  
   `cache/powergrid_states.json` has all states set to `"somewhat unlikely"/"likely"/"somewhat likely"` uniformly. This means state sampling in rank mode is essentially random across all state values — the LLM's belief encoding has no real signal. This is not a bug per se but limits rank mode's interpretability.

2. **Powergrid prompt mismatch (now fixed).**  
   The original prompt asked the agent to "prioritize stability" (pick most stable), but the stated research goal is "pick most unstable for protection triage". The evaluator oracle was also argmin (most stable). Both have been updated to argmax (most unstable) in this adaptation.

3. **`response_format={"type": "json_object"}` is hardcoded.**  
   This works for GPT-4o/GPT-4 but may not work for all local models (Llama, Mistral, Gemma). The new `llm_client.py` handles this via `LLM_JSON_MODE` env var.

4. **No seed control for rank sampling.**  
   State-action pair sampling in `sample_state_action_pairs()` uses `np.random.choice` without a fixed seed. Results are not reproducible across runs unless the random state is fixed externally.

5. **`summarize()` in prompt_utils is only used by FarmAgent.**  
   PowerGridAgent and TradeAgent never call `summarize()`. The function is dead code for powergrid runs.

6. **Evaluation (`evaluate_dellma.py`) requires `choix` which is not in conda env by default.**  
   The `rank` / `rank-minibatch` evaluation paths use `choix.ilsr_pairwise` / `choix.ilsr_top1`. Zero-shot/CoT evaluation does not require `choix`.

7. **`stab` sign convention is counter-intuitive.**  
   `stab > 0` = unstable, `stab < 0` = stable. This is the opposite of a typical stability margin. The convention is documented in the dataset but easy to confuse when reading code.
